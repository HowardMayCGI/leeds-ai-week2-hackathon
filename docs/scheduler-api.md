# Schedule proposal API

`POST /api/schedules` accepts the complete selected list, including clinical-record medicines and UI additions, and the routine gathered in the UI. It returns a JSON proposal with warnings. It is stateless: no NHS number is needed, no record is fetched or modified, and nothing is saved. All knowledge remains demonstration-only and not clinically validated.

## Call it

Start the API with `pnpm nx run api:dev`, then:

```sh
curl http://127.0.0.1:3001/api/schedules \
  -H 'Content-Type: application/json' \
  --data-binary @docs/examples/schedule-request.json
```

The checked-in [example request](examples/schedule-request.json) mixes record medicines and a user-entered iron product. The [example response](examples/schedule-response.json) is generated by the bundled API. It schedules levothyroxine before food, metformin with meals, and iron at least four hours apart from levothyroxine, including on successive days. The quantities in this synthetic example illustrate the contract, not recommended doses.

From the browser, use the same-origin URL:

```ts
import type {
  ScheduleRequest,
  ScheduleResponse,
  ScheduleValidationError,
} from "@hackathon/api-contract";

async function proposeSchedule(inputs: ScheduleRequest): Promise<ScheduleResponse> {
  const response = await fetch("/api/schedules", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(inputs),
  });
  if (!response.ok) {
    const error = (await response.json()) as ScheduleValidationError;
    throw new Error(
      error.errors?.map((item) => `${item.path}: ${item.message}`).join("; ") || error.message,
    );
  }
  return response.json();
}
```

Display all warnings, including non-blocking warnings. Only read `schedule.doses` when `status === 'proposed'`; `blocked` has `schedule: null`. A proposed schedule is not clinical clearance or an instruction to change prescribed treatment.

## Request

The full shared types are in `packages/api-contract/src/index.ts` (`ScheduleRequest`, `ScheduleMedicine`, `ScheduleResponse`).

| Field                             | Meaning                                                                                                                                                                                                                                                                    |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `routine`                         | Same shape as the UI's `Routine`: `wake`, `sleep`, and `meals.breakfast/lunch/dinner`. All times are 24-hour `HH:MM`. Use `null` for skipped meals. Meals must be ordered and fall in the waking day; overnight sleep is supported.                                        |
| `medicines`                       | Complete selected list, including additions. An empty list is valid.                                                                                                                                                                                                       |
| `id`, `source`                    | Unique ID across the full list and `record` or `user`. IDs are echoed so the UI can join results to its own items. `source` records provenance; it does not authenticate a prescription.                                                                                   |
| `name`                            | Display label. Known products use the server catalogue label in output. Names alone are never used for ingredient matching.                                                                                                                                                |
| `code` + `system`, or `productId` | Use the coded clinical product, or a local product ID from the existing UI catalogue. Do not supply both: the local catalogue has no verified SNOMED mappings. Both may be absent for a manual unmatched entry.                                                            |
| `dose`                            | `quantity`, optional `quantityMax`, and `unit`. Uses the UI's `Dose` quantity convention; convert the older API's `dose.value` to `quantity`. Units are preserved, including insulin units or patches. No dose, strength or unit conversion is performed.                  |
| `regimen`                         | One of the variants below. Do not infer a frequency from product strength or missing fields.                                                                                                                                                                               |
| `administration`                  | Optional additional constraints confirmed from instructions: `food` is `any`, `with-food` or `empty-stomach`. For empty stomach, supply `emptyStomach.beforeMinutes` and `afterMinutes`. Submitted constraints supplement known server rules; they cannot switch them off. |
| `instructions`                    | Original text to show beside the proposal. It is not parsed into constraints.                                                                                                                                                                                              |
| `instructionsConfirmed`           | When text is supplied, explicitly confirm that it has been checked and its timing requirements encoded. Without confirmation, the response is blocked. This flag cannot override interactions, dose reviews, duplicate ingredients or server requirements.                 |

Regimens:

```json
{ "kind": "daily", "dosesPerDay": 2, "minimumGapMinutes": 240 }
```

Daily regimens also accept `fixedTimes` (exactly one distinct time per dose) and optional supported FHIR `when` codes: `ACM`, `ACD`, `ACV`, `C`, `CM`, `CD`, `CV`, `MORN`, `EVE`, `HS`, `WAKE`. Meal-specific codes require that meal to exist. Before-meal codes also need an explicit or known administration gap. For the demo, morning means the first four waking hours, evening the last six, bedtime the last hour, and waking the wake time. These conventions are not universal clinical definitions.

`{ "kind": "as_needed" }` preserves the item separately and generates no fixed doses. Its interactions still apply. Spacing involving an as-needed item is returned as conditional guidance rather than enforced at an invented dose time. Maximum PRN doses need separate confirmation.

`{ "kind": "interval", "every": { "value": 3, "unit": "d" }, "anchor": "2026-10-24T08:00:00+01:00" }` is recognised but returns an `unsupported_interval_regimen` blocking warning. The daily service does not turn hourly, weekly or every-N-days courses into daily schedules; calendar-based support is follow-on work.

## Response

HTTP 200 means the submitted plan was evaluated. A response can still be blocked:

```json
{
  "status": "blocked",
  "demoOnly": true,
  "clinicallyValidated": false,
  "schedule": null,
  "warnings": [
    {
      "code": "interaction_review",
      "severity": "error",
      "blocking": true,
      "medicineIds": ["warfarin", "naproxen"],
      "message": "Contact your GP or anticoagulation team promptly to check this combination. Taking the medicines at different times does not remove the risk.",
      "action": "medication_review"
    }
  ]
}
```

This is an excerpt; full responses also include rule `versions`, matched `interactions` and linked `sources`. Versions identify the scheduler, both administration rule sets, interaction dataset and local catalogue.

For `proposed`, `schedule` contains the submitted `routine`, ordered `doses` and `asNeeded` medicines. Each dose has `medicineId`, canonical `name`, `source`, unchanged `dose`, `time`, `dayOffset`, `minute` and visible `instructions`. `minute` is measured from midnight before waking; `dayOffset: 1` means the following calendar day. Display that offset for overnight doses rather than sorting by clock time alone.

Warnings have stable codes, severity, a `blocking` flag, relevant medicine IDs and an action (`information`, `confirm_instructions`, `medication_review`, `change_routine`). Important cases include unknown products, incomplete administration coverage, unconfirmed text, unspecified dose intervals, dose ranges, PRN guidance, conditional gaps, unmet preferences, duplicate ingredients, interactions needing review, unsupported intervals, impossible constraints and search exhaustion. Missing knowledge can yield provisional times with warnings; it never establishes safety.

HTTP errors are 400 for invalid JSON/schema/routine (schema errors include field paths), 403 for origin rejection, 405 for wrong method (`Allow: POST`), 413 above 128 KiB and 415 for a non-JSON media type. Unexpected failures return a generic 500. Requests allow up to 40 medicines, 8 daily doses per medicine and 120 regular doses overall. Quantity bounds are input limits, not therapeutic dose checks. Unsupported fields are rejected rather than silently ignored.

## Planning behaviour

The API resolves both coded products and local demo catalogue ingredients, then checks interactions across the full submitted list. Known prescriber/dose reviews and overlapping ingredients block the whole proposal; no partial timetable is returned that might hide excluded medicines. Names and client-supplied ingredient guesses cannot bypass the product lookup.

The planning core in `packages/medicines/src/daily-plan.ts` performs a deterministic feasibility search at one-minute resolution. It prefers routine events and a spread through the waking day. It does not promise a globally optimal or clinically approved timetable. Required food constraints, fixed times, intervals and directional/separation rules are never relaxed. Preferences can be missed, with a warning. Posture and water advice are included for the UI; remaining-upright time must fit before sleep, but actual behaviour cannot be verified.

Same-medicine intervals and inter-medicine gaps are checked against copies of the timetable on the preceding and following day. The independent checker in `daily-plan-checker.ts` verifies every successful assignment. Search is limited to 200,000 candidate visits; exhaustion returns `search_limit`, not a false assertion that no valid plan exists. Positive directional cycles are rejected before search.

Administration comes from the sourced exact-product examples plus the existing, explicitly unvalidated local-catalogue demonstration rules. Local levothyroxine/simvastatin variants use the corresponding demo administration recipes without asserting a mapping to another product's SNOMED code. This remains a small knowledge base; it does not comprehensively screen duplicate drug classes, conditions, allergies, renal function, therapeutic doses or missing supplements.

## UI integration and deployment

The current UI still invokes its existing client-side proposal builder. This change supplies the API and shared contract; it does not rewrite the UI journey or saved-schedule format. A caller can map checked record medicines and additions into this contract, call the endpoint on Check answers, and render dose rows plus warnings.

Map local UI frequencies to `daily.dosesPerDay` (1, 2, 3 or 4), or `as_needed`. Copy `Dose` directly; preserve original instruction wording and record timing codes. Use `productId` for local catalogue selections and `code`/`system` for actual clinical products. For `/schedule-inputs` results, resolve the reported issues before constructing the request; use its explicit `prescriptionTiming`, not the medication endpoint's legacy display defaults. Do not drop unsupported original instructions while mapping them.

Both local HTTP and Lambda adapters forward JSON bodies, including base64 Lambda events. CloudFront's existing `/api/*` behaviour now uses the seven-method option needed to forward POST, while the Lambda handler still limits each route to its supported methods. Static content remains GET/HEAD. [AWS documents the allowed method combinations](https://docs.aws.amazon.com/cloudfront/latest/APIReference/API_AllowedMethods.html). No new AWS resources are added; the configuration change must be deployed before the hosted endpoint accepts POST. Nothing has been deployed by this implementation task.

Verification includes domain tests against exhaustive small examples, API/service tests, real loopback HTTP tests, Lambda body forwarding and mocked infrastructure checks.
